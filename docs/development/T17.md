# T17 성능·장애·카오스 검증 (프롬프트 17)

마지막 갱신: 2026-10-07. 기준: [27-performance-chaos](../../SecDrill-docs/docs/27-performance-chaos.md).

**이 단계에서 성능·부하·soak 측정은 수행하지 않았다.** 지정 하드웨어·staging·강한 runtime이 없어(D-10) 목표 수치를 측정할 수 없다. 문서의 성능 가정을 측정 결과로 제시하지 않는다(프롬프트 요구). 측정 가능한 것은 **장애 불변식의 정확성**뿐이며, 부하·회복시간·지연 목표는 미검증으로 남긴다.

## 1. 실제 환경 기록

| 항목 | 이 개발 호스트(실측) | 27의 가정 baseline |
|---|---|---|
| CPU | 10 vCPU (Apple arm64, Darwin 25.6.0) | Control 4 + DB 4 + Runner 합계 64, ≥2 Runner 호스트 |
| 메모리 | 32 GiB (전체 1대) | Control 8 + DB 8 + Runner 128 GiB |
| runtime | Docker 28.0.4, 단일 데몬, local-trusted만 | strong runtime microVM(Firecracker 계열), 전용 Runner 호스트 |
| JDK/Kotlin/Gradle | JDK 21.0.10, Kotlin 2.4.10, Gradle 9.8 | 동일 스택 |
| staging | 없음 | 운영과 같은 강한 runtime·합성 콘텐츠 |
| 자원 예약 | 없음(개발 박스, 다른 프로세스·컨테이너와 공유) | 20 Lab 예약 40 vCPU/40 GiB + compile/채점 peak 여유 |

결론: 단일 공유 개발 박스에 강한 runtime·전용 Runner 풀·staging이 없다. 따라서 API p95, Lab READY p95, 패치 평가 p95, SYSTEM_ERROR율, orphan 회수 시간, 1×/2×/3× 부하·2시간 soak는 **여기서 측정 불가**다. 측정은 지정 호스트 확보 후 2절 방법으로 수행하고 결과를 첨부한다.

## 2. 측정 목표 상태

모두 **미검증**(측정 안 함/불가). 아래는 목표값이며 현재 달성 주장 아님.

| 지표 | 목표(가정) | 상태 |
|---|---|---|
| API p95 (store·SSE 제외) | ≤300ms | 미측정(하드웨어·부하 의존) |
| Lab request→READY p95 | ≤60s | 미측정(강한 runtime·전용 호스트 필요, D-10) |
| 패치 accepted→evaluation p95 | ≤30s | 미측정(grading-strong 없음; local-trusted는 demo) |
| SYSTEM_ERROR | <1% | 미측정(부하 필요); 단건 경로의 SYSTEM_ERROR 처리는 불변식으로 입증(3절) |
| stale 결과 반영 | 0건 | 불변식 입증(3절); 부하 하 재확인 미측정 |
| orphan 회수 | ≤5분 | 회수 동작 불변식 입증(3절); 시간 목표 미측정 |
| 지연 분해 queue/provision/compile/test/ingest | — | 미측정(방법은 2.1) |

### 2.1 재현 가능한 측정 방법(staging에서 수행)

- 워크로드(27): 50 학습자(20 실제 Lab), 사용자당 REST 0.2rps, 활성 Lab당 합성 API 5rps, 공식 제출 분당 5, SSE 50, Session당 evidence ≤1,000/min. 5분 ramp → 30분 steady → 5분 cooldown → 2시간 soak. 1×·2×·3×로 반복.
- 지연 분해: 제출 수락→outbox→dispatch→claim→compile→test→ingest→evaluation 구간을 `ExecutionCompleted`/evidence 타임스탬프와 job state 전이로 나눈다. API 지연은 actuator `http.server.requests`(T16 관측)로, queue 대기·orphan 지연은 T16 게이지(`secdrill.outbox.oldest.age.seconds`, `secdrill.labs.cleanup.pending`)로 관측한다.
- 기록: 가정·환경·버전·그래프·불변식 검사·실패 원인·개선·재측정(27). 3×에서 성공 latency 유지를 약속하지 않는다.

## 3. 장애 불변식 추적 (정확성, 지금-검증)

27 장애 실험의 **불변식**은 기존 통합 테스트로 입증된다. 아래 테스트는 이번에 재실행해 통과를 확인했다(비-Docker 5종) 또는 이전 clean 전체 검사에서 통과했다(Docker 2종, 이 호스트에서는 부하 flake 있음). **입증되는 것은 불변식(정확성)이며, 회복 시간·부하 하 동작은 미측정이다.**

| 27 실험 | 기대 불변식 | 입증 테스트 | 비고 |
|---|---|---|---|
| publish 직후 process kill | duplicate 가능, 제출 유실 없음 | `CrashBeforeCommitTest`, `OutboxDeliveryTest`(broker outage·duplicate once) | 재실행 통과. 2분 backlog 재개 시간은 미측정 |
| test 중 Agent kill | lease 회수·late token 차단 | `JobLeaseTest`(lease expiry 거절·3회 후 SYSTEM_ERROR), `OpsControlsTest`(quarantine late token STALE) | 재실행 통과. 60초 재할당 시간은 미측정 |
| broker 60초 단절 | Outbox 보존·무한 재시도 없음 | `OutboxDeliveryTest`(outage 후 row 유지, 재confirm) | 재실행 통과. T05에서 3회 반복 확인 이력 |
| store GET 실패 | SYSTEM_ERROR, 사용자 FAIL 아님 | `JobLeaseTest`(platform error→backoff→SYSTEM_ERROR, never FAIL) | 재실행 통과. store-miss는 grading에서 platform error로 매핑 |
| result duplicate/역순 | active evaluation 1개 | `OutboxDeliveryTest`(duplicate once), `JobLeaseTest`(stale 거절), `EvidenceLedgerTest`(same source event once) | 재실행 통과 |
| DB 30초 단절 | 미커밋 성공 응답 없음 | `CrashBeforeCommitTest`(트랜잭션 원자성) | 원자성 입증. **DB를 요청 중간에 끊는 주입은 미실행**(부분) |
| create 후 callback 유실 | runtime label로 orphan 인식 | `LabLifecycleTest`(reconcile orphan·late callback 회수), `LocalTrustedIsolationTest`(취소 후 생성 회수·위조 label 미삭제) | Docker; 이전 clean 통과, 호스트 flake. 5분 회수 시간 미측정 |
| noisy neighbor output/memory | 다른 Session·host 보호 | `LocalTrustedIsolationTest`(PID 상한·출력 1 MiB truncate·memory flood cgroup kill) | Docker; 이전 clean 통과. 동시 부하 하 cross-session 영향 미측정 |
| Control 다운 상태 TTL | hard TTL 자율 종료 | `LocalTrustedIsolationTest`(Control 미도달 중 로컬 hard TTL), `LabLifecycleTest`(idle/hard TTL) | Docker; 이전 clean 통과 |
| clock skew ±30초 | seq 순서·occurredAt 불확실 | `EvidenceLedgerTest`(late observation 시간 유지, seq는 서버 순서) | 재실행 통과 |

재실행 통과(이번): `CrashBeforeCommitTest`·`OutboxDeliveryTest`·`JobLeaseTest`·`EvidenceLedgerTest`·`OpsControlsTest`.

## 4. 안전·중단 (절차)

주입은 staging 합성 환경에서만, pilot는 승인된 창에서만(27). 중단 조건: 5xx>5% 2분, host RAM>90%, cleanup 지연>5분, cross-session 영향. 중단 후에도 orphan·DLQ·pending 삭제를 끝까지 확인한다. **운영 사용자 영향 실험은 승인 없이 하지 않는다.** 이 환경에는 운영 사용자가 없다(합성만).

## 5. 미검증·Blocker·다음 작업

- **Blocker(D-10)**: 강한 runtime·전용 Runner 호스트·staging 부재로 성능·부하·soak·대부분의 회복시간 목표가 미측정. local-trusted 결과는 demo이며 격리·성능 증거가 아니다.
- 부분 공백: DB를 요청 중간에 끊는 주입, store GET 실패를 grading 입력에 직접 주입하는 카오스 실험은 전용 테스트가 없다(원자성·platform-error 경로로 간접 입증). clock skew는 ledger 레벨만.
- 부하 하 공정 대기·429·store 성장·회수 지연은 미측정.
- **다음**: 지정 호스트·강한 runtime·staging 확보 후 2.1 방법으로 baseline→1×→2×→3×→soak 측정, 10개 주입 실험 수행, 목표 미달 원인 수정·재측정, 결과를 이 문서에 첨부.
